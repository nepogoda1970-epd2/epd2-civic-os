# PACK-15 - Traceability matrix

```text
PACK-15 IMPLEMENTATION CANDIDATE
PARTIAL LOCAL VERIFICATION ONLY
DEPENDENCY INSTALLATION BLOCKED BY SANDBOX NETWORK POLICY
EXTERNAL CI NOT YET VERIFIED
NOT FINAL PASS
NOT PRODUCTION READY
NOT LEGALLY ACTIVATED
```

This document maps every one of the 154 acceptance criteria in
`docs/packs/PACK-15/PACK-15-ACCEPTANCE-MATRIX.md` to the artefact that
implements it and to the executed test that proves it. It exists because
the other three PACK-15 handover documents argue in prose, and prose is
the medium in which an unimplemented control is easiest to describe as if
it were finished. A row here marked `SATISFIED` means one thing and only
one thing: a named test function ran under real `pytest` in this round
and asserted the property. It does not mean an author believes the
property holds, that a design document requires it, or that a reviewer
read the code and was satisfied. Where no test ran, the row says so, and
the weaker status is used whenever the mapping was arguable - a wrong
`SATISFIED` is worse than a conservative `PARTIAL`, because the next
round will read this file as the list of things it no longer has to
check, and a criterion falsely retired here is a control that quietly
stops existing. The specific damage is concrete: if `AC-P15-061` were
marked satisfied on the strength of a design note rather than the
field-pair scans in the two persistence modules, the pairing prohibition
that makes "did this person vote" unanswerable would rest on nothing an
automated check would notice breaking. The counts in section 27 are
therefore deliberately unflattering. Every path cited below was checked
to exist, and every test function named was read out of the module it is
attributed to.

Status vocabulary, used exactly:

- `SATISFIED` - an implementation artefact exists and an executed,
  passing test asserts it.
- `IMPLEMENTED - NOT EXECUTED` - the artefact exists but its test could
  not run here. This is the status of every criterion whose only evidence
  is frontend code: `node_modules` is unavailable, and no vitest,
  Playwright, axe or `next build` run happened (`PACK-15-TEST-EVIDENCE.md`
  section 4).
- `PARTIAL` - closed in part; the artefact column names what remains.
- `NOT CLOSED BY THIS PACK` - owned by a later pack or an external layer,
  named in the artefact column.
- `NOT APPLICABLE` - with the reason.

The status word uses a hyphen rather than a dash because this file is
ASCII-only by rule.

eligibility to a membership record type", "the required import-path and

this round built none of them. The result is that AC-P15-009, -012,
-015, -091, -092 and -129 rest on the observable fact that no such import
or client exists today, with nothing that fails when someone adds one.
That is exactly the failure mode the privacy evidence warns about in a
different register: a rule in application code survives until the next
person who needs a number in a hurry, and a rule in nobody's code at all
survives less well than that. The second cluster was smaller but
sharper, and building this matrix is what found it: AC-P15-037 was
`PARTIAL` because `required_assurance_satisfied` was carried across the
trust boundary, persisted, and never read - the assurance requirement was
asserted by the identity side and silently discarded by the voting side,
a fail-open in a control the specification marks fail-closed. It has
since been closed: `AssertionVerifier.assert_valid` now refuses an
assertion whose assurance flag is false, and a test asserts the refusal.
It is recorded here rather than quietly repaired because a traceability
matrix that only maps controls to tests, and never notices a control with
no path, is a filing system rather than evidence - and this one earned
its keep on the first pass.

sandbox: `node_modules` cannot be installed, so five frontend files and
