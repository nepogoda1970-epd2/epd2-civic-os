# Service Boundaries

Настоящий документ фиксирует обязательные границы между будущими модулями
и сервисами EPD² Civic OS, вытекающие из архитектурных инвариантов ТЗ-00
(`docs/canonical/TZ-00-domain-event-canon.md`, раздел 4).

## Один владелец сущности

У каждой канонической сущности есть ровно один модуль-владелец (см.
`docs/architecture/data-ownership.md` и раздел 22 канона —
«Матрица владения сущностями»). Другие модули не изменяют сущность
напрямую и не обращаются напрямую к её хранилищу.

## Запрет прямого доступа к чужой базе

Модуль не может:

- читать таблицы другого модуля;
- изменять их;
- использовать общий ORM для всей платформы;
- выполнять межсервисные SQL-запросы.

## Интеграция только через API и события

Взаимодействие между модулями допускается только через:

- версионированный API;
- версионированное событие (см. раздел 21 канона — «Стандарт события»);
- утверждённый read model;
- специальный audit export.

## Shared packages не содержат бизнес-логики

Пакеты в `packages/` (`epd2-core` для Python, `epd2-types` для TypeScript)
предоставляют только:

- инфраструктурные типы;
- константы версий;
- универсальные утилиты (например, генерацию и валидацию UUID).

Они не должны содержать доменных сущностей, доменных статусов, бизнес-правил
или бизнес-логики конкретного контура.

## Потенциальная отделяемость сервиса

Репозиторий на этом этапе организован как модульный монорепозиторий (см.
`docs/adr/ADR-001-repository-strategy.md`), но каждый будущий сервис должен
проектироваться так, чтобы его можно было выделить в независимый деплой-юнит
без нарушения перечисленных выше границ.

## Реализация в CLAUDE-PACK-02

`services/account-service`, `services/identity-service`,
`services/eligibility-service`, `services/credential-service`,
`services/audit-core` — первые пять независимых модулей, реализующих
правила этого документа буквально, а не только декларативно:

- у каждого — собственный `pyproject.toml`, `src/`, `tests/`, storage
  interface и in-memory reference adapter (пока без production-базы —
  см. `docs/review/KNOWN_LIMITATIONS.md`);
- ни один из пяти сервисов не импортирует `src/` другого — проверено
  структурно (AST-анализ импортов, не текстовый grep) в
  `tests/repository/test_service_boundaries.py`, которая проходит по
  полной матрице N×N запрещённых пар для всех пяти сервисов разом, и
  дополнительно в
  `services/eligibility-service/tests/test_domain.py::test_eligibility_service_has_no_import_dependency_on_identity_service`
  как узкая, service-локальная проверка того же правила;
- взаимодействие между сервисами идёт только через явный вызов
  прикладной команды одного сервиса, куда caller передаёт результат
  другого сервиса как input value — не через общее хранилище;
- единственная намеренная межсервисная зависимость — все четыре
  доменных сервиса (`account-`, `identity-`, `eligibility-`,
  `credential-service`) зависят от `epd2-audit-core`, чтобы записывать
  собственные `AuditEvent` (см. `docs/architecture/audit-kernel.md`);
  зависимость однонаправленная — Audit Core не знает ни о каком
  доменном сервисе;
- `packages/python/epd2-core` расширен только инфраструктурными
  примитивами (canonical event envelope, UUID/time helpers, generic
  validation utilities, version constants, reason-code infrastructure
  без доменных решений) — без единой доменной сущности, статуса или
  бизнес-правила, специфичного для одного контура (пакет 4.2).

Полное разделение личности и участия (`Account` → `IdentityRecord` →
`EligibilityRule`/`Decision`/`Snapshot` → `ParticipationCredential`)
описано отдельно в
`docs/architecture/identity-participation-separation.md`.

## Финансовый контур (canon 19f, канон `0.8.0`) — границы доверия

Канон `0.8.0` добавил финансовый ограниченный контекст (canon 19f) с
владельцем `Finance Service`. Сервис **не реализован**; границы ниже —
каноническое требование к будущему раунду реализации, а не описание
существующего кода.

- **Импорт только общих пакетов.** Будущий `finance-service` импортирует
  `epd2_core` и `epd2_audit_core` и ничего больше (INV-03, 19f.23).
- **Факты чужих контуров — только через опубликованный интерфейс.**
  Организационный scope и институциональное полномочие читаются у
  `organization-service` (19e); правовое дело, срок, уведомление, правовой
  эффект, legal hold и класс хранения — у `compliance-service` (PACK-09),
  исключительно как типизированные ссылки (19f.22).
- **Документы и доказательства не принадлежат финансам.** Байты документа,
  подпись, цепочка версий, содержимое доказательства и цепочка владения
  остаются за PACK-11; финансовая запись хранит только безопасную ссылку и
  никогда не выводит из неё подлинность, подписанность, допустимость или
  публикуемость (19f.22).
- **Нет ребра в сторону голосования.** Ни импорта, ни поля, ни ссылки в
  сторону `Ballot`, `VoteEnvelope`, `Tally`, `Delegation` или
  избирательного credential; финансовая запись не может стать мостом
  корреляции к голосованию (19f.13 ФИН-36, раздел 23).
- **Внутренние границы модулей нагружены смыслом.** Бюджетный модуль не
  пишет в регистр учёта; модуль проекций не выполняет авторитетную запись;
  модуль ревизии не пишет в проверяемый агрегат; разрешать целевую ссылку
  на сторону (`FinancePartyHandle`) вправе только выделенный модуль
  реестра сторон (19f.15, ADR-048).
- **Лоббизм и встречи — не финансовый контур.** Реестр контактов, встреч,
  доступа и нефинансового влияния принадлежит PACK-35; финансы владеют
  только финансово измеримым влиянием и его раскрытием (19f.9, 19f.22).

## Document Service (PACK-11, `FIR-ROADMAP-001`, `FIR-INV-010`)

Реализован в справочной форме (`reference_implementation`) раундом
PACK-11; ADR-055 – ADR-060. Канон `0.8.0` не изменяется: раздел 19f.22 уже
закрепляет за PACK-11 байты документов, авторитетные версии, подписи,
криптографические цепочки версий, содержимое доказательств и цепочку
ответственного хранения — этот раунд реализует уже назначенное владение.

- **Импорт только общих пакетов.** `document-service` импортирует
  `epd2_core` и `epd2_audit_core` и ничего больше. В частности он **не**
  импортирует `epd2_compliance_service`: PACK-09 владеет сроками хранения,
  правовым удержанием и авторизацией уничтожения, и все три поступают сюда
  как типизированные непрозрачные ссылки в собственном модуле
  `references.py`. Импорт превратил бы задокументированную границу в
  runtime-ребро, которое рефакторинг мог бы незаметно расширить.
- **PACK-11 — лист.** Ни один сервис не импортирует `document-service`.
  Placeholder-типы PACK-09 (`DocumentRef`, `EvidenceRef`, `MinutesRef`,
  `NoticeProofPackageRef`) и PACK-10 (`DocumentReference`,
  `EvidenceReference`) намеренно **не** переписаны под реальные типы
  PACK-11 — граница, ради которой они существуют, сохраняется (OD-21).
- **Содержимое хранится здесь и не покидает контур.** Это единственный
  контур, владеющий байтами документов, — именно поэтому ни один payload
  события, ни одно поле метаданных аудита и ни одна проекция не несут
  содержимого, извлечённого текста, рендиции, значения подписи или строки
  заголовка. Единая точка выхода — `domain.assert_emission_safe`.
- **Нет ребра в сторону голосования.** Ни импорта, ни поля, ни ссылки в
  сторону `Ballot`, `VoteEnvelope`, `Tally`, `Delegation` или
  `ParticipationCredential`; протокол может _фиксировать_, что голосование
  состоялось, но никогда не несёт ссылку, связывающую бюллетень с лицом
  (INV-01, INV-02, INV-03).
- **Утверждения не выводятся.** Подписанность и допустимость — записанные
  определения, привязанные к точному хешу версии, а не вычисленные выводы;
  отсутствие определения сообщается как явное `not_determined`.
- **Внутренние границы модулей нагружены смыслом.** `versions` не знает о
  жизненном цикле документа; `projections` не выполняет авторитетную
  запись и не может быть сконструирован с `is_authoritative = True`;
  `storage` не принимает решений на управляемых основаниях; ни один порт
  хранилища не объявляет метод удаления.
